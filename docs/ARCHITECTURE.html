The Problem

AI agents can destroy merchant money while technically "growing sales"

Razorpay knows what products sell for. It doesn't know what they cost. An AI agent proposing discounts without access to cost of goods will optimize for order value — not merchant profit.

AI proposes: 30% off running shoes
Paid by customer₹944.30
Razorpay fees (2% + 18% GST)−₹22.29
Cost of goods (COGS)−₹830.00
Merchant profit₹92.01 (9.74%)
Required margin floor18.00%
Shortfall per sale−₹70.19
The agent "succeeded." It created an order. But the merchant lost money on every unit.
❓
Razorpay has no cost data
The Orders API carries the selling price. COGS, return rates, and margin floors are merchant-side knowledge the platform doesn't have.
🤖
LLMs optimize for what they can measure
An AI agent sees order count and basket size. It cannot see cost of goods, MDR non-refundability, or return-risk exposure.
⚡
Agents act fast, at scale
A single AI loop can propose hundreds of orders per minute. Without authorization controls, losses scale with throughput.
The Thesis

Authorization is not the AI's job

The AI decides what it wants to accomplish.
It cannot decide what financial actions it is authorized to take.

The Centrepiece

DENY → Constraint → Replan → ALLOW

The agent isn't blocked. It is constrained. When Arbiter DENY's a proposal, it returns the exact ceiling — and the agent replans within it. The objective stays constant. The strategy changes.

Components

Every part has exactly one job

🧮

MarginEngine

Pure arithmetic. Zero LLM. Zero network calls. Zero database. Takes items and paid amount, returns exact margin percentage and safe discount ceiling.

fee = paid × 2%
gst = fee × 18%
cogs = sum(catalog[sku] × qty)
margin = paid − fee − gst − cogs
ceiling = cogs / (k − floor)
← closed-form, not guessed
🔒

PolicyEngine — 7 rules, fail-closed

Deterministic. Zero LLM. DENY always wins over ALLOW. Rules evaluated in order — first violation stops evaluation.

1COGS not in trusted catalogDENY
2Return rate > 25% (MDR risk)DENY
3Margin below floor + ceilingDENY
4Discount > 20% auto-approveGATE
5Order amount > ₹5,000GATE
6Velocity > 10/minDENY
7All checks passedALLOW
🪪

Action Passport

Every execution requires a scoped, time-bounded, hash-signed token. The agent receives this — never credentials. Cannot be forged, replayed, or extended.

allowed_action: DISCOUNT_OFFER
max_discount_pct: 22.74
authorized_amount: ₹1,106.18
policy_version: 1
valid_until: +5 min TTL
passport_hash: 9ed913f4b4e2…
🔁

Failure Handling — UNKNOWN state

When Razorpay returns a 5xx, we don't know if a charge occurred. We never guess. We never retry automatically. We quarantine and wait for human resolution.

5xx received
→ exec_status = UNKNOWN
→ quarantine row inserted
→ SAFE_HALT
→ no retry
→ no assumption
"We do not say 'no charge occurred.'"
🔐

TOCTOU Revalidation

Before every Razorpay call, Arbiter reloads the catalog and policy from disk, re-enriches items, and re-runs PolicyEngine. If economics changed — DENY.

At execution time:
1. Reload catalog
2. Reload policy
3. Re-enrich COGS
4. Re-run PolicyEngine
5. Execute if still ALLOW
🔑

GATE Re-authorization

When a merchant approves a GATE action from the dashboard or email, Arbiter doesn't just execute — it revalidates economics and kill switch state first.

On human approve:
1. Check COGS still valid
2. Re-run PolicyEngine
3. Check kill switch
4. Then execute
🚨

Kill Switch

One button pauses all autonomous execution. The AI can still propose. It cannot auto-execute. All ALLOW decisions become GATE requiring human approval.

When active:
ALLOW → GATE
AI can: propose
AI cannot: execute
Backend-enforced

Experiment verdict
The experiment did not produce positive aggregate uplift. Arbiter reports this rather than hiding it. The control plane optimizes for authorized economics — not vanity growth metrics. A dashboard that shows only green rows is fabricated.
"A control plane that cannot be bribed by vanity metrics is the point."
Integrity: Statistical power LOW (n=50 underpowered). Results are directional only — not causal evidence of growth. "Converted" = order created in Razorpay test mode, not payment captured.
